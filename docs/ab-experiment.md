# Task 4 (bonus) — A/B промптів

**Підзадача для експерименту:** компонент форми швидкого додавання задачі
(`QuickAddTask`) — єдине поле «назва задачі» + кнопка.

**Умови:** обидва промпти виконані в **чистому контексті** (окремий агент, який
нічого не знає про цю сесію та не бачив коду застосунку), та сама модель
(Claude Opus 5), той самий інструментарій. Обидва писали результат у файл у
тимчасовій теці й не мали доступу до вже написаного `app/`.

---

## Промпт A — базовий

```text
Зроби форму для додавання задачі в застосунку тайм-трекера. React + TypeScript.
```

## Промпт B — структурований (роль + контекст + обмеження + критерії + формат)

```text
**Роль:** Ти senior frontend-інженер, який пише продакшн-код на React 19 +
TypeScript у Next.js 16 (App Router).

**Контекст:** Застосунок «Workday Time Tracker» — особистий трекер робочого
часу. Уся UI побудована на дизайн-системі Porsche Design System v4, пакет
`@porsche-design-system/components-react`, імпорт через підшлях `/ssr`
(обов'язково для Next.js). Доступні компоненти: `PInputText`, `PButton`,
`PText`, `PHeading`, `PTag`. Стан задач живе у батьківському компоненті;
форма отримує колбек `onAdd(name: string): void`.

**Завдання:** Напиши компонент `QuickAddTask` — форма швидкого додавання
задачі, у якій користувач вводить ЛИШЕ назву задачі.

**Обмеження:**
1. Тільки компоненти дизайн-системи, жодного голого HTML для інпутів/кнопок.
   Виняток — `<form>` як обгортка.
2. `PInputText` має обов'язковий проп `name`. Подія зміни — це `onInput`, який
   отримує `CustomEvent`; нативний таргет треба кастити до `HTMLInputElement`.
3. `PButton` за замовчуванням має `type="submit"`.
4. Компонент має бути клієнтським (`'use client'`).
5. Без зовнішніх залежностей (без react-hook-form, zod тощо).

**Критерії приймання:**
- Enter у полі додає задачу (без окремого обробника `keydown` — через нативний
  submit форми).
- Порожня назва або назва лише з пробілів НЕ створює задачу; кнопка в такому
  стані задизейблена.
- Назва обрізається (`trim`) перед передачею в `onAdd`.
- Після успішного додавання поле очищається.
- Є обмеження довжини назви.
- Лейбл присутній для скрінрідера, але візуально прихований.

**Формат відповіді:** Лише готовий файл компонента з мінімальними коментарями
там, де рішення неочевидне.
```

## Що саме пішло не так у A

1. **Scope creep — головна проблема.** На запит «форма додавання задачі» агент
   спроєктував менеджер задач: опис, проєкт, пріоритет (radio group), оцінка
   часу з парсером формату `1h 30m`, дедлайн, теги, чекбокс «запустити таймер
   одразу». Це 409 рядків замість 57 — **у 7 разів більше коду**, і майже весь
   він суперечить продуктовій ідеї «створити задачу, ввівши лише назву».
2. **Дизайн-систему проігноровано повністю.** Нуль PDS-компонентів, 10 голих
   HTML-контролів. Промпт A її не згадував — і агент не мав звідки про неї
   дізнатися. Це прямо ламає головну вимогу домашки (UI з компонентів DS).
3. **Якість коду сама по собі була висока** — `useId`, `aria-invalid`,
   `aria-describedby`, `role="alert"`, фокус на першому невалідному полі, чисті
   хелпери під юніт-тести. Агент не «полінувався»; він старанно вирішив **не ту
   задачу**.

## Висновок

Різниця не в токенах — вона мізерна (39 241 проти 36 108, ~9 %). Різниця в
тому, що **A довелося б викинути повністю**, а B можна комітити. Якби рахувати
чесно, вартість A — це не 39 тис. токенів, а 39 тис. плюс ще один-два раунди
«ні, прибери опис/проєкт/теги, використай Porsche Design System», плюс час на
рев'ю 409 рядків непотрібного коду.

Найдорожчий рядок у промпті B — не критерії приймання, а **контекст**: назва
дизайн-системи та підшлях імпорту `/ssr`. Без нього агент фізично не міг
вгадати правильну відповідь. Другий за важливістю блок — **обмеження**, бо саме
вони зупиняють scope creep («вводить ЛИШЕ назву»).

Практичний висновок для наступних домашок: критерії приймання пишемо тоді, коли
хочемо *передбачувану* реалізацію, але контекст (стек, версії, бібліотеки)
пишемо **завжди** — це різниця між «код, що компілюється в моєму проєкті» і
«код взагалі».
