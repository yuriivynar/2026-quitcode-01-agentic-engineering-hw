# Task 4 (bonus) — A/B промптів (демо-прогін)

> Еталонний приклад. Підзадача для експерименту: **форма заявки на PDS**.
> Кожен промпт виконувався у чистому контексті.

## Промпт A — базовий

```text
Зроби форму для заявок клієнтів у React.
```

## Промпт B — структурований

```text
Роль: senior React-розробник, працюєш з Porsche Design System v4
(@porsche-design-system/components-react).

Контекст: Vite + React TS застосунок "Lead Desk" для заявок клієнтів агенції.

Задача: форма заявки як частина App.tsx.

Вимоги (acceptance criteria):
- поля: ім'я (обов'язкове), email (обов'язкове), бюджет (select з 4
  діапазонів), повідомлення (textarea, обов'язкове)
- ЛИШЕ компоненти PDS: PInputText, PInputEmail, PSelect/PSelectOption,
  PTextarea, PButton; жодних нативних input
- uncontrolled-підхід: submit через FormData (компоненти form-associated)
- після submit — form.reset()

Обмеження: не додавай CSS-фреймворків; layout — простий grid у index.css.
Формат відповіді: лише код, без пояснень.
```

## Порівняння

| Критерій | A (базовий) | B (структурований) |
|---|---|---|
| Компоненти | нативні `<input>` + самописний CSS | одразу PDS, як вимагалось |
| Патерн стану | 4 × `useState` + onChange на кожне поле | uncontrolled + FormData (менше коду) |
| Ітерацій до цілі | 3 («перепиши на PDS», «прибери useState», стилі) | 1 |
| Токени (оцінка) | ~7K за три обміни | ~3K за один |

## Висновок

Базовий промпт дає «форму взагалі» — валідну, але не ту: без дизайн-системи і
з зайвим станом. Структурований — одразу цільову, бо обмеження («лише PDS»,
«uncontrolled») зрізають простір рішень. Різниця ×2+ у токенах і часі. На
Воркшопі 2 перетворимо такі промпти на повторно використовувані шаблони.
